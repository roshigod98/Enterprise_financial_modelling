# The Oundle Deck — Financial Modelling Dashboard

**Interactive supplier, pricing, demand and risk analysis for a student enterprise.**

A Python + Streamlit decision-support application built by **Roshan Narayan** in connection with **The Oundle Deck**, a pupil-created Oundle School playing-card enterprise entered into the **2026 Peter Jones Foundation Tycoon Enterprise Competition**.

> **Project context:** The six-person team reported approximately **350 decks sold** and **£1,100 in revenue**, and won the **Key Stage 3–4 award** at the 2026 Tycoon ceremony. These are *team-reported business outcomes*, not outputs generated by the financial model or audited results.

## Overview

A fixed-price Excel calculation quickly became insufficient when comparing suppliers, minimum order quantities, sales uncertainty and limited starting capital. I created an interactive tool to evaluate the trade-offs between **price, demand, supplier costs, upfront funding and profit** — without assuming that forecast demand or supplier quotes were known precisely.

This repository documents the technical project, not the team's complete business accounts. *The Oundle Deck* was a collaborative enterprise; the financial model was my individual software contribution.

## Features

| Module | What it does |
| --- | --- |
| Supplier evaluation | Loads indicative supplier quotes from a CSV, compares costs and allows manual supplier assumptions |
| Scenario modelling | Fixed or variable selling prices, sales volumes, production quantities and extra costs |
| Unit economics | Revenue, COGS, contribution, margins, illustrative pre-/post-tax profit, inventory |
| Pricing & demand | Optional two-point linear demand assumption linking customer price to expected sales |
| Break-even & financing | Trading break-even, upfront cash requirement, cash recovery, £1,000 goodwill loan ceiling |
| Sensitivity | Interactive profit curves, price–volume heatmaps, scenario envelopes and supplier comparisons |
| Monte Carlo | Seeded uniform *what-if scenario sampling* for viability and funding coverage |
| Communication | Plotly charts, narrative explanations, a glossary and illustrative charity/team allocations |

**Sales channel:** Oundle School billing, rather than an online payment processor. The model therefore does not assume card-processing or customer-shipping fees.

## Tech stack

**Python · Streamlit · NumPy · pandas · Plotly · pytest · GitHub Actions**

The financial calculations are separate from the interface, making them testable without Streamlit.

## Installation

Python **3.11+** recommended.

```bash
git clone https://github.com/roshigod98/Enterprise_financial_modelling.git
cd Enterprise_financial_modelling
python3 -m venv .venv
```

Activate the environment: `source .venv/bin/activate` (macOS/Linux) or `.venv\Scripts\Activate.ps1` (Windows PowerShell).

```bash
python -m pip install -r requirements.txt
python -m streamlit run app/main.py
```

The input data lives in `data/quotes_clean.csv`. To add a supplier, edit that file or choose **Custom (manual entry)** in the dashboard. **Missing quotes or shipping charges are unknown; they must not be interpreted as free.**

## Critical financial assumptions

**Tycoon goodwill funding is a repayable loan, not revenue or profit.** The Peter Jones Foundation states that teams repay their initial goodwill loan and may retain profits afterwards. The dashboard therefore separates **trading performance** from **upfront financing**. [Tycoon FAQ](https://tycoon.com/faqs/) · [Competition terms](https://tycoon.com/terms-conditions/)

Two similarly named metrics answer different questions:

- **Trading break-even:** how many sold decks are needed for revenue to cover the costs attributable to sales plus fixed costs. This can be zero when fixed costs are zero, even if ordering inventory still requires cash.
- **Cash recovery:** how many decks need to be sold for **net sales receipts** to recover the cash paid to buy the initial batch. It does not subtract inventory acquisition a second time.

The app uses **illustrative 20% VAT and 20% profit-tax conventions** for educational scenarios, not a determination of tax owed by a school enterprise. Tax, actual VAT registration and any distribution of profits require confirmation with the school's finance team.

The Monte Carlo output represents the **proportion of scenarios sampled within assumptions you choose**. It is not an empirically calibrated probability of success; the default demand anchor points are also adjustable *assumptions*, not a fitted economic demand curve.

For complete definitions and limitations, read **[Model assumptions](docs/MODEL_ASSUMPTIONS.md)**.

## Testing

```bash
python -m pytest -q
```

The tests focus on the distinction between a loan and income, cash vs accounting break-even, VAT conversion, profit allocation, supplier parsing and scenario edge cases.

## What I learned

This project brought together **business decisions and computational modelling**. It highlighted why supplier prices alone are insufficient: minimum orders, cash commitments, uncertainty about demand and the distinction between financing and profit can change which business plan is viable.

It also exposed a valuable lesson in software engineering: a professional dashboard needs **verifiable definitions, robust calculations and clear caveats**, not just impressive-looking charts.

## Further development

Potential improvements include observed sales data vs forecast comparisons, explicit school-bill payment timing, historic quote provenance, supplier lead-time risk, repeat-order cashflow and better demand calibration.
